Banco de dados

Com o crescimento do usuário BASE, um servidor não é suficiente, e precisamos de vários servidores: um para tráfego web/móvel, o outro para o banco de dados (Figura 1-3). Que bancos de dados usar?

Você pode escolher entre um banco de dados relacional tradicional e um banco de dados não relacional. Vamos examinar suas diferenças.

Bancos de dados relacionais também são chamados de sistema de gerenciamento de bancos de dados relacionais (RDBMS) ou banco de dados SQL. Os mais populares são o banco de dados MySQL, Oracle, PostgreSQL, etc.

Bancos de dados relacionais representam e armazenam dados em tabelas e linhas. Você pode realizar operações de junção usando SQL em diferentes tabelas de banco de dados.

Bancos de dados não relacionais também são chamados de bancos de dados NoSQL. Os mais populares são CouchDB, Neo4j, Cassandra, HBase, Amazon DynamoDB, etc. [2]. Essas bancos de dados são agrupadas em quatro categorias: armazenamentos de chave-valor, lojas de gráficos, lojas de colunas e lojas de documentos. Operações de adesão geralmente não são suportadas em bancos de dados não relacionais.

Para a maioria dos desenvolvedores, bancos de dados relacionais são a melhor opção porque eles têm sido ao redor por mais de 40 anos e historicamente, eles têm funcionado bem. No entanto, se bancos de dados relacionais não são adequados para seus casos de uso específico, é fundamental explorar além de bancos de dados relacionais. Bancos de dados não relacionais podem ser a escolha certa se • sua aplicação requer uma latência super baixa.

• Seus dados não estão estruturados, ou você não tem nenhum dado relacional.

• Você só precisa serializar e desserializar dados (JSON, XML, YAML, etc.).

• Você precisa armazenar uma enorme quantidade de dados.

scaling vertical vs scaling horizontal scaling vertical, referido como "escale-se", significa o processo de adicionar mais energia (CPU, RAM, etc.) aos seus servidores. scaling horizontal, chamado de "escala-out", permite que você escale adicionando mais servidores em seu conjunto de recursos.

Quando o tráfego está baixo, scaling vertical é uma ótima opção, e a simplicidade do scaling vertical é sua principal vantagem. Infelizmente, vem com sérias limitações.

• scaling vertical tem um limite difícil. É impossível adicionar CPU ilimitado e memória a um único servidor.

• scaling vertical não tem failover e redundância. Se um servidor cair, o site/app cai completamente.

scaling horizontal é mais desejável para aplicações em larga escala devido às limitações do scaling vertical.

Replicação do banco de dados Citado da Wikipédia: "Replicação de banco de dados pode ser usada em muitos sistemas de gerenciamento de banco de dados, geralmente com uma relação master/slave entre o original (master) e as cópias (slaves)" [3].

Um banco de dados master geralmente só suporta operações de gravação. Um banco de dados slave recebe cópias dos dados do banco de dados master e só suporta operações de leitura. Todos os comandos modificadores de dados como inserir, excluir ou atualizar devem ser enviados para o banco de dados master. A maioria das aplicações requer uma proporção muito maior de leituras para escrever; assim, o número de bancos de dados slave em um sistema é geralmente maior do que o número de bancos de dados master. A figura 1-5 mostra um banco de dados master com vários bancos de dados slave.

Vantagens da replicação do banco de dados: • Melhor desempenho: no modelo master-slave, todas as gravações e atualizações acontecem em nós master, enquanto que as operações de leitura são distribuídas em nós slave. Este modelo melhora o desempenho porque permite que mais consultas sejam processadas em paralelo.

• Confiabilidade: se um de seus servidores de banco de dados for destruído por um desastre natural, como um tufão ou um terremoto, os dados ainda estão preservados. Você não precisa se preocupar com a perda de dados porque os dados são replicados em vários locais.

• Alta disponibilidade: replicando dados em diferentes locais, seu site permanece em Operação mesmo que um banco de dados esteja offline como você pode acessar dados armazenados em outro servidor de banco de dados.

Cache

Um cache é uma área de armazenamento temporário que armazena o resultado de respostas caras ou dados frequentemente acessados na memória para que os requisições subsequentes sejam atendidos mais rapidamente. Como ilustrado na Figura 1-6, toda vez que uma nova página da web carrega, uma ou mais chamadas de banco de dados são executadas para buscar dados. O desempenho da aplicação é muito afetado por ligar para o banco de dados repetidamente.

O cache pode atenuar esse problema.

O nível cache é uma camada temporária de armazenamento de dados, muito mais rápido do que o banco de dados. CAP theorem

CAP theorem afirma que é impossível um sistema distribuído fornecer ao mesmo tempo mais de duas dessas três garantias: consistência, disponibilidade e tolerância à partição. Vamos estabelecer algumas definições.

ConsistênciaConsistência significa que todos os clientes veem os mesmos dados ao mesmo tempo, não importa qual nó eles se conectam.

Disponibilidade: A disponibilidade significa que qualquer cliente que solicita dados recebe uma resposta mesmo que alguns dos nós estejam em baixo.

Tolerância a partições: uma partição indica uma ruptura de comunicação entre dois nós.

Detecção de falhas Em um sistema distribuído, é insuficiente acreditar que um servidor está desligado porque outro servidor diz isso. Normalmente, requer pelo menos duas fontes independentes de informação para marcar um servidor.

Uma solução melhor é usar métodos de detecção descentralizada de falhas como protocolo de fofocas.

O protocolo de fofocas funciona da seguinte forma: • Cada nó mantém uma lista de membros, que contém membros. IDs e batimentos cardíacos contadores.

• Cada nó aumenta periodicamente seu contador de batimentos cardíacos.

• Cada nó periodicamente envia batimentos cardíacos para um conjunto de nós aleatórios, que por sua vez se propagam para outro conjunto de nós.

• Uma vez que nós recebem batimentos cardíacos, a lista de membros é atualizada para as últimas informações.

• Se o batimento cardíaco não aumentou por mais do que períodos pré-definidos, o membro é considerado offline.

Redirecionamento 302. . Um redirecionamento 302 significa que o URL é "temporariamente" movido para o URL longo, o que significa que requisições subsequentes para o mesmo URL será enviado para o serviço de encurtamento URL primeiro. Então, eles são redirecionados para o longo servidor URL.

Você pode pensar na web como um gráfico direcionado onde as páginas da web servem como nós e hiperlinks (URLs) como bordas. • O feed de notícias é gerado em tempo real e pode ser empurrado para amigos imediatamente.

• buscar feed de notícias é rápido porque o feed de notícias é pré-computado durante o tempo de gravação.

• Se um usuário tem muitos amigos, buscar a lista de amigos e gerar notícias para todos eles são lentos e demorados. Chama-se problema de chave de atalho.

Prós:

Contras:

• buscar o feed de notícias é lento, pois o feed de notícias não é pré-computado.

Polling

Como mostrado na Figura 12-3, polling é uma técnica que o cliente pergunta periodicamente ao servidor se há mensagens disponíveis. Dependendo da frequência polling, polling pode ser caro. Poderia consumir preciosos recursos de servidor para responder a uma pergunta que oferece não como resposta na maioria das vezes.

Long polling

Porque polling pode ser ineficiente, a próxima progressão é long polling (Figura 12-4).

Em long polling, um cliente mantém a conexão aberta até que haja novas mensagens disponíveis ou um limite de tempo de espera tenha sido alcançado. Uma vez que o cliente recebe novas mensagens, ele imediatamente envia outro requisição para o servidor, reiniciando o processo. long polling tem alguns inconvenientes: • Sender e receptor podem não se conectar ao mesmo servidor de bate-papo. Servidores baseados em HTTP geralmente são stateless. Se você usar round robin para Load Balancing, o servidor que recebe a mensagem pode não ter uma longa conexão polling com o cliente que recebe a mensagem.

• Um servidor não tem jeito de dizer se um cliente está desconectado.

• é ineficiente. Se um usuário não conversa muito, long polling ainda faz conexões periódicas após os intervalos.

WebSocket é a solução mais comum para enviar atualizações assíncronas de servidor para cliente. A figura 12-5 mostra como funciona.

Armazenamento

Neste ponto, temos servidores prontos, serviços funcionando e integrações de terceiros completas. No fundo, a pilha técnica é a camada de dados. A camada de dados geralmente requer algum esforço para obtê-lo correto. Uma decisão importante que devemos tomar é decidir sobre o tipo certo de banco de dados para usar: bancos de dados relacionais ou bancos de dados NoSQL? Para tomar uma decisão informada, nós examinará os tipos de dados e os padrões de leitura/escrita.

Dois tipos de dados existem em um sistema de bate-papo típico. O primeiro são dados genéricos, como perfil de usuário, configuração, lista de amigos de usuário. Esses dados são armazenados em bancos de dados relacionais robustas e confiáveis.

Replicação e sharding são técnicas comuns para satisfazer os requisitos de disponibilidade e escalabilidade.

O segundo é único para sistemas de bate-papo: dados de histórico de bate-papo. É importante entender o padrão de leitura/escrita.

• A quantidade de dados é enorme para sistemas de bate-papo. Um estudo anterior [2] revela que o mensageiro Facebook e o WhatsApp processam mensagens 60 bilhões por dia.

• Só conversas recentes são acessadas com frequência. Usuários geralmente não procuram por bate-papos antigos.

• Embora o histórico de bate-papo muito recente seja visto na maioria dos casos, usuários podem usar recursos que requerem acesso aleatório de dados, como busca, ver suas menções, saltar para mensagens específicas, etc. Esses casos devem ser suportados pela camada de acesso de dados.

• A relação de leitura para gravação é sobre 1:1 para 1 em aplicativos de bate-papo 1.

Selecionar o sistema de armazenamento correto que suporta todos os nossos casos de uso é crucial. Recomendamos armazenamentos de chave-valor pelas seguintes razões: • armazenamentos de chave-valor permitem fácil scaling horizontal.

• armazenamentos de chave-valor fornece baixa latência para acessar dados.

• bancos de dados relacionais não lidam com cauda longa3Os dados estão bem. Quando os índices crescem, o acesso aleatório é caro.

• armazenamentos de chave-valor são adotados por outras aplicações de bate-papo comprovadamente confiáveis. Por exemplo, o mensageiro Facebook e o Discord usam o armazenamentos de chave-valor. Facebook mensageiro usa HBase [4], e Discord usa Cassandra [5].

Desconexão do usuário Todos desejamos que nossa conexão com a internet seja consistente e confiável. No entanto, nem sempre é o caso, portanto, devemos abordar este assunto em nosso projeto. Quando um usuário se desconecta da internet, a conexão persistente entre o cliente e o servidor é perdida. Uma maneira ingênua de lidar com a desconexão do usuário é marcar o usuário como offline e mudar o status para online quando a conexão se restabelecer. No entanto, essa abordagem tem uma grande falha. É comum que os usuários se desconectem e se reconectem à internet frequentemente em pouco tempo. Por exemplo, conexões de rede podem ser ligadas e desligadas enquanto um usuário passa por um túnel. Atualizar o status on-line em cada desconexão/reconexão faria o indicador de presença mudar com muita frequência, resultando em má experiência do usuário.

Introduzimos um mecanismo cardíaco para resolver esse problema. Periodicamente, um cliente online envia um evento cardíaco para servidores de presença. Se os servidores de presença recebem um evento cardíaco dentro de um determinado tempo, digamos x segundos do cliente, um usuário é considerado como online. Caso contrário, está desligado.

Fluxo de download

Fluxo de download é ativado quando um arquivo é adicionado ou editado em outro lugar. Como um cliente sabe se um arquivo é adicionado ou editado por outro cliente? Há duas maneiras de um cliente saber: • Se o cliente A estiver online enquanto um arquivo é alterado por outro cliente, o serviço de notificação informará o cliente A que as mudanças são feitas em algum lugar para que ele precise de pull os dados mais recentes.

• Se o cliente A estiver offline enquanto um arquivo é alterado por outro cliente, os dados serão salvos no cache. Quando o cliente offline está on-line novamente, ele puxa as últimas mudanças.

Uma vez que um cliente sabe que um arquivo é alterado, ele primeiro solicita metadados via servidores API, em seguida, baixa blocos para construir o arquivo. A figura 15-15 mostra o fluxo detalhado. 3. Servidores API chamam metadados DB para buscar metadados das mudanças.

4. Metadados são devolvidos aos servidores API.

Economize espaço de armazenamento. Para suportar o histórico da versão do arquivo e garantir a confiabilidade, várias versões do mesmo arquivo são armazenadas em vários data centers. • Mantenha apenas versões valiosas, alguns arquivos podem ser editados com frequência. Por exemplo, salvar cada versão editada para um documento altamente modificado pode significar que o arquivo é salvo em 1000 vezes em um curto período. Para evitar cópias desnecessárias, podemos limitar o número de versões salvas. Damos mais peso às versões recentes.

Tratamento de falhas

Falhas podem ocorrer em um sistema em grande escala e devemos adotar estratégias de design para lidar com essas falhas. Seu entrevistador pode estar interessado em ouvir sobre como você lida com as seguintes falhas do sistema: falha • load balancer: se um load balancer falhar, o secundário ficará ativo e pegará o tráfego. load balancers geralmente monitoram uns aos outros usando um batimento cardíaco, um sinal periódico enviado entre load balancers. Um load balancer é considerado como um fracasso se ele não enviou um batimento cardíaco por algum tempo.

• Se um servidor de bloqueio falhar, outros servidores pegam trabalhos inacabados ou pendentes.

• Falha de armazenamento na nuvem: baldes S3 são replicados várias vezes em diferentes regiões. Se os arquivos não estiverem disponíveis em uma região, eles podem ser obtidos de diferentes regiões.

Mesmo que um servidor possa manter muitas conexões abertas, ele não pode reconectar todas as conexões perdidas ao mesmo tempo. Reconectar com todos os clientes perdidos é um processo relativamente lento.

• Falha na fila de backup: filas são replicadas várias vezes. Se uma fila falhar, os consumidores da fila podem precisar se inscrever novamente na fila de backup.

Como qualquer entrevista de System Design perguntas, não há solução perfeita. Cada empresa tem suas restrições únicas e você deve projetar um sistema para se adequar a essas restrições. Conhecer o trade-offs de suas escolhas de design e tecnologia é importante. Se sobrarem alguns minutos, você pode falar sobre escolhas de design diferentes.

Por exemplo, podemos carregar arquivos diretamente para armazenamento na nuvem do cliente em vez de passar por servidores de bloco. A vantagem desta abordagem é que faz o upload de arquivos mais rápido porque um arquivo só precisa ser transferido uma vez para o armazenamento na nuvem. Em nosso projeto, um arquivo é transferido para bloquear servidores primeiro, e depois para o armazenamento na nuvem. No entanto, a nova abordagem tem algumas desvantagens: • Primeiro, o mesmo bloco, compressão, e lógica de criptografia deve ser implementado em diferentes plataformas (iOS, Android, Web). É propensa a erros e requer muito esforço de engenharia. Em nosso projeto, todas essas lógicas são implementadas em um lugar centralizado: servidores de bloco.

• Segundo, como um cliente pode ser facilmente hackeado ou manipulado, implementar a lógica criptografada do lado do cliente não é o ideal.

Outra evolução interessante do sistema é mover a lógica on-line/offline para um serviço separado. Vamos chamá-lo de serviço de presença. Ao mover o serviço de presença de servidores de notificação, a funcionalidade online/offline pode ser facilmente integrada por outros serviços.
